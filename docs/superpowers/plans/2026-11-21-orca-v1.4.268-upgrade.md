# Orca-Wails 升级至 Orca v1.4.268 的开发计划

**目标** 通过现有打包流程验证 macOS ARM64 和 Windows x64 的 `v1.4.268` Core，验证通过后更新各自的正式锁文件。

**实现依据** 使用项目 README 的「跟进官方 Orca」流程。`scripts/follow-orca.py` 负责生成候选锁，现有 macOS Bun 和 Windows Node 脚本负责各自的打包及运行验证。

## 2026-11-21 查版结果

- 官方稳定版 `v1.4.268` 于北京时间 11:50 发布。`core-version.macos-arm64.json` 和 `core-version.json` 均锁在 `v1.4.267`。GitHub 已提供对应 macOS ZIP 和 Windows 安装包的 SHA-256。[官方发布](https://github.com/stablyai/orca/releases/tag/v1.4.268)
- `v1.4.268` 标签解析为 `5dc5548b4570b276f231d81fbb51f8f7a066e40d`。GitHub 显示两个发布标签的历史已分叉，`.268` 有 442 个独有提交，`.267` 有 8 个。需要核对两端源码快照及实际发布包。[标签比较](https://github.com/stablyai/orca/compare/v1.4.267...v1.4.268)
- 两端的 `node-runtime-pin.ts` 和 `orcad-artifacts.ts` SHA-256 一致，并与当前 Windows 锁记录匹配。包内 Node 标记、Web 资源清单和插件补丁仍待候选准备步骤验证。[运行时锁定源码](https://github.com/stablyai/orca/blob/v1.4.268/src/shared/node-runtime/node-runtime-pin.ts) · [Core 产物清单](https://github.com/stablyai/orca/blob/v1.4.268/src/shared/remote-runtime/orcad-distribution/orcad-artifacts.ts)
- 上游 `orcad` 构建新增 Codex 历史引用 worker。会话库的 `journal_connector_replies` 新增可空 `took_ms` 列，迁移保持 `user_version` 原值。两项变化都需要用实际包和测试数据验证。[Core worker](https://github.com/stablyai/orca/pull/45221) · [会话库迁移](https://github.com/stablyai/orca/blob/v1.4.268/src/main/native-chat/agent-session-journal/connector-replies/journal-connector-replies-schema.ts)
- Windows Git 命令取消涉及进程捕获逻辑，值得在候选 Core 上回归。发布说明中的桌面关闭重构和 Web 重试分别落在上游 Electron 桌面和移动端源码。Wails 的 Core 重启、退出清理和 Web 配对通过现有打包流程单独验收。[Windows Git 取消](https://github.com/stablyai/orca/pull/44961) · [上游桌面关闭流程](https://github.com/stablyai/orca/pull/45071) · [移动端 Web 重试](https://github.com/stablyai/orca/pull/45891)
- `python3 scripts/test-follow-orca.py` 已通过 4 项测试。候选包构建、两端冒烟和导入兼容性均待执行。

## 实施步骤

1. **P0｜生成候选锁。** 执行 `python3 scripts/follow-orca.py --tag v1.4.268 --prepare`。验收时确认 `dist-core/follow/v1.4.268/` 中两份候选锁都指向已确认的标签提交和官方产物校验值，macOS Node 标记和 Web 清单通过脚本校验。若 `scripts/macos-data-plugins.patch` 应用失败，仅针对失败的补丁位置核对上游两端源码，修复后重跑准备命令。
2. **P0｜验证 macOS ARM64。** 用候选锁提取 Core，运行 Bun 校验并生成独立冒烟应用。

   ```sh
   candidate=dist-core/follow/v1.4.268
   python3 scripts/extract-macos-core.py --download-orca \
     --version-file "$candidate/core-version.macos-arm64.json" --output "$candidate/macos"
   python3 scripts/verify-bun-macos.py \
     --version-file "$candidate/core-version.macos-arm64.json" --core-dir "$candidate/macos"
   ./scripts/build-macos.sh --smoke-test --archive "$candidate/macos/bootstrap-core.zip"
   ```

   在独立数据目录和端口验证首次启动、真实 PTY、Web 配对、关闭后重新打开窗口，以及退出后 Core 子进程清理。用 `.267` 和 `.268` 数据副本核对 `orca-profile-index.json`、`profile-state.db`、`agent-session-domain.db`，通过 `PRAGMA table_info(journal_connector_replies)` 验证 `took_ms` 迁移。运行 `go test ./internal/official`，确认项目及会话历史可导入。导入通过后更新 `internal/official/official.go` 的版本门槛。若导入回归，将其作为 macOS 升级的阻塞项。
3. **P0｜验证 Windows x64。** 将候选锁交给 Windows 11 x64 的 `scripts/extract-headless.ps1`，用产出的 ZIP 构建便携版。

   ```powershell
   $candidate = 'dist-core/follow/v1.4.268'
   pwsh -File scripts/extract-headless.ps1 -VersionFile "$candidate/core-version.json" `
     -OutputDirectory "$candidate/windows"
   pwsh -File scripts/build-windows.ps1 -Archive "$candidate/windows/orca-core-v0.0.1-1.4.268-x86_64-pc-windows-msvc.zip"
   ```

   验收 Node 启动、ConPTY、取消 Git 操作及 Job 进程树清理，以及 WebView2 加载、配对和窗口重开。当前 `v1.4.267` 锁也仅记录静态包校验。Windows 真机或具备对应能力的 CI 结果是更新该平台正式锁的前提。
4. **P1｜回归并更新正式锁。** 运行 `go test ./...`、`go vet ./...`、`python3 scripts/test-follow-orca.py` 和 README 中的 Node 测试。用各平台的测试数据验证运行版本显示为 `v1.4.268`，确认 Codex 历史读取能加载新 worker，并用测试备份验证旧 Core 仍可启动。每个平台通过验收后，复制对应候选锁到仓库根目录，并为 Windows 记录实际验证结果。

## 实施记录

- macOS ARM64 已构建 `v1.4.268`。插件补丁适配了 5 处上游变动。Core 补齐了 Codex 历史引用和占用统计 worker，两个 worker 都通过了 Bun 实际调用。
- macOS 验证了首次启动、同目录重启、真实 PTY、WebKit 首次配对、关闭和重开窗口，以及退出时的进程清理。用两版官方 Core 生成的隔离数据验证了导入、备份和 `took_ms` 迁移，也验证了旧 Core 能用保留的数据重新启动。
- Windows x64 外壳交叉构建通过。官方安装包、432 个 Core 文件哈希和 1,551 个 Web 文件已核验。官方 Core 缺少两个已引用的 Codex worker，且当前没有 Windows 主机执行 ConPTY、Job 和 WebView2 验收。Windows 正式锁为 `v1.4.267`。
